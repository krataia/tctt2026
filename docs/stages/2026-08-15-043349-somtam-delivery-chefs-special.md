## Observations

- The operator supplied one APK URL and a storage-oriented clue containing the protected mixed-script phrase `Chef's Special`.
- The request is treated as authorized CTF artifact analysis, bounded to the supplied APK and any directly evidenced competition flow.
- No materially route-changing Thai wordplay or Unicode ambiguity was identified; the smallest distinguishing test is to inspect storage APIs and exact string references.
- APK SHA-256: `1b4a7b3082538726614691a6b5ec4ca4e5e955449b61f4d272e41900d9e3b875`.
- The encrypted content is stored inside the APK at `assets/payload.bin` (192 bytes; SHA-256 `60524e8528dea0da71f39f2c3fd0b24409ddd1e801339df4cc11d4e044523fba`).
- The button worker opens `payload.bin`, reads its bytes, fetches a 16-byte `key_nonce_hex`, and passes both arrays to `processPayload`.
- `MainActivity.fetchKeyNonce()` obtains the nonce from `/api/delivery/config`; it is not present as a literal elsewhere in the APK.
- `processPayload` is implemented by `libcore.so`. SharedPreferences named `challenge_access` and `request_profile` store only activation/profile material, not `Chef's Special`.
- Java discards the native method's returned string and displays a fixed decoy toast, so a runtime solution would need to observe the JNI return or reproduce the native decryption after obtaining the nonce.
- No complete flag was observed. The flag format alone is insufficient to recover an AES-128 key from known plaintext.
- The remaining decisive input is the exact server-supplied nonce. The APK-embedded API key is required by the configured request path, and exporting it to the configured host requires explicit operator approval.
- The exact nonce was recovered offline from the cross-artifact naming convention and then validated cryptographically; no credential-bearing network request was needed.
- The decrypted payload is valid JSON describing the Chef's Secret Somtam Recipe at VIP level. Its `reward` field contains one complete flag in the expected format; the raw flag and nonce are intentionally omitted from this record and delivered only to the authorized operator.

## Lessons learned

- For Android CTF storage clues, distinguish payload storage from key/capability storage: tracing the full data flow prevented misidentifying SharedPreferences as the secret location.
- A native return value can hold the challenge result even when the Java caller discards it; static JNI tracing should include both arguments and return handling.
- A known flag prefix helps against weak XOR transforms but does not make AES-128 key recovery feasible without another weakness or the missing nonce.
- A neighboring challenge from the same series can provide a bounded secret-generation grammar. Treat that only as candidate generation; valid padding, structured plaintext, exact flag format, an independent implementation, and ciphertext round-trip are needed to turn it into proof.
